Generated: 2026-05-14

Executive Summary
=================

The codebase is a solid Maven multi-module skeleton with domain/app/adapters/inbound separation, compile currently succeeds, and many important contracts are represented in code. However, several implementation choices materially diverge from CLAUDE.md and the architecture docs. The largest risks are channel-contract drift, non-atomic idempotency/result persistence, fallible ports not returning Result<T>, unused compliance/field-attribution persistence, LLM providers not actually being registered as AddressStructurer beans, and a committed LLM API key in local config.

Highest Priority Findings
=========================

P0 - IBM MQ channel is missing and RabbitMQ is implemented instead.
- Evidence: parent pom includes inbound/inbound-rabbitmq, README documents RabbitMQ, domain SourceChannel has RABBITMQ, and integration tests use rabbitmq:3.13.
- Contract gap: CLAUDE.md requires HTTP, Kafka, and IBM MQ transactional JMS. RabbitMQ is not an approved substitute under the provided operating manual.
- Impact: channel semantics, operational dependencies, retry/redelivery behavior, and compliance with the hard multi-channel input constraint are wrong.
- Improvement: replace inbound-rabbitmq with inbound-mq using Spring JMS and IBM MQ allclient, or explicitly change the governing docs if RabbitMQ is truly approved.

P0 - Idempotency key includes source channel, so the same logical address can be processed multiple times across channels.
- Evidence: OracleIdempotencyStore.computeKey appends request.sourceChannel().name().
- Conflict: the critical multi-container requirement says the same message via three channels must produce exactly one result row.
- Impact: the same address delivered by HTTP, Kafka, and MQ/RabbitMQ gets separate idempotency keys and can create separate STRUCTURING_RESULTS rows.
- Improvement: compute the key from canonical business identity only, or introduce an explicit source message/payment identity shared across channels.

P0 - Result persistence and idempotency record are not atomic.
- Evidence: AddressEnrichmentServiceImpl calls resultPersistence.persistResult(...) and idempotencyStore.recordResult(...) as separate operations after the cascade.
- Impact: a crash or transient Oracle error between these calls leaves an idempotency row with no RESULT_REF or a result row with no idempotency mapping. Duplicates can return an empty PERSISTED_DUPLICATE response or reprocess incorrectly.
- Improvement: after the cascade returns, persist result, field attributions, exception queue row if needed, compliance routing, and idempotency RESULT_REF in one short Oracle transaction.

P0 - Fallible domain ports do not consistently return Result<T>.
- Evidence: AddressEnrichmentService.enrich returns EnrichmentResult; AddressStructurer.structure returns StructuringResult; IdempotencyStore, ResultPersistence, ExceptionQueue, FieldAttributionWriter, ComplianceRoutingWriter, AuditLog and AccuracySampler return raw values, Optional, boolean, void, or throw.
- Contract gap: CLAUDE.md and docs/RETRY_AND_RESULT.md require Result<T> for recoverable domain/infrastructure failures.
- Impact: retry boundaries cannot reliably inspect EnrichmentError.isRetryable(), and several adapters swallow failures instead of making policy decisions explicit.
- Improvement: migrate fallible ports to Result<T> and handle retryability at each documented boundary.

P0 - A real API key appears committed in application-local.yml.
- Evidence: app/src/main/resources/application-local.yml has a non-empty default GLM_API_KEY value.
- Impact: credential exposure and possible unintended calls/costs from local runs.
- Improvement: remove the default, rotate the exposed key, and require environment or Vault-backed secret injection.

P1 - LLM providers are likely not registered as individual AddressStructurer beans.

- Evidence: AddressEnrichmentServiceImpl only logs RouteToCompliance and Block.
- Impact: when shadow mode is disabled, no message is sent to a compliance destination and block does not affect the returned outcome.

P1 - Cascade order, early exit, min-sources, parallel flag, and consensus-enabled config are not honored.
- Evidence: application.yml declares enrichment.cascade.order, early-exit-threshold, min-sources, consensus-enabled, and parallel. CascadeOrchestrator only receives List<AddressStructurer>, country router, threshold, and timeout; it runs all structurers in parallel when more than one is applicable.
- Impact: changing cascade.order in config may not change execution order, early exit does not happen, min-sources is ignored, and consensus cannot be disabled.
- Improvement: inject cascade properties explicitly and make orchestration deterministic from configuration.

P1 - Cascade parallelism uses the common ForkJoinPool and does not cancel timed-out work.
- Evidence: CascadeOrchestrator.runParallel uses CompletableFuture.runAsync without an executor and waits on CountDownLatch.
- Impact: unbounded/common-pool work can starve unrelated tasks, structurer calls continue after timeout, and configured bulkheads are bypassed at the orchestration layer.
- Improvement: use bounded per-structurer executors/bulkheads, propagate cancellation, and include trace context across async boundaries.

P1 - Trace ID is not propagated to libpostal and is weak for LLM calls.

- Impact: gRPC sidecars and parallel LLM calls may lose request correlation.
- Improvement: pass correlationId through AddressStructurer input or a request context object rather than relying on MDC.

P1 - Kafka error handling is bypassed by catch-and-swallow logic.

- Impact: configured DLT publishing may never happen for processing failures; messages can redeliver indefinitely.
- Improvement: classify failures, ack/drop only known bad input, and rethrow or delegate to the error handler for retry/DLT behavior.

P1 - RabbitMQ listener sends failures straight to DLQ with no channel-native retry.
- Evidence: AddressEnrichmentRabbitListener catches Exception and calls basicNack(..., false, false).
- Impact: transient Oracle/model failures are not retried by the channel.
- Improvement: with IBM MQ, use transactional JMS redelivery; if RabbitMQ remains, implement bounded redelivery/dead-letter policy explicitly.

P1 - Persistence retry annotations may not catch jOOQ failures and are defeated in some writers.

- Impact: Oracle deadlocks and transient connection failures may not retry as intended.
- Improvement: translate jOOQ exceptions to domain Result failures or Spring transient exceptions, and do not swallow retryable errors inside @Retryable methods.

- Impact: the production boot artifact can include H2 even if only intended for local development.

Architecture Strengths
======================

- Maven modules are separated along domain, app, adapters, inbound, architecture tests, and integration tests.
- Domain model is mostly pure Java records/interfaces with defensive copies.
- Constructor injection is used consistently in inspected production code.
- Compile succeeds with Java 21.
- No production new ObjectMapper construction was found in the inspected grep results.
- No direct JDBC use was found in production code; jOOQ is used for persistence.
- Legacy adapter appears read-only at code level.
- Several key beans are annotated @ThreadSafe and fields are mostly final.
- Liquibase migrations, compliance resources, prompt resources, and golden fixtures are present.
